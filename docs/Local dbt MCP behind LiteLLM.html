Local dbt MCP behind LiteLLM

Our team runs its own LiteLLM, the Gateway, on a Shared host. It serves dbt Metadata tools (lineage, node details, list) to apps, scripts and notebooks, and forwards every model call to the Managed LiteLLM that another team runs. The Managed LiteLLM needs no changes. ClickHouse is never contacted. We build and test this in a Devcontainer that runs the same image.

Brief for a review session

Everything below is written so a reader with no prior context can challenge the design. The button copies the full page, with the diagram described in words, for pasting into another session.

Constraints and context

  • The Managed LiteLLM is run by another team at a shared internal URL, and we cannot change its configuration. It has issued us one key, for gpt-5.6-sol.
  • We host dbt-mcp ourselves, not the remote dbt platform MCP server.
  • Callers are apps, scripts and notebooks on other machines, not IDE agents.
  • Callers need metadata only: models, sources, lineage, node details. They don't run dbt commands or query the warehouse.
  • It runs on one Shared host for the whole team. Development happens in a Devcontainer.
  • The dbt project is dbt_dwh/ in the monorepo, on ClickHouse, with dbt-core 1.12.6 and profile dev.

What the design decides

  1. Our own LiteLLM, the Gateway, runs on the Shared host through docker compose. The Devcontainer uses the same compose file with a dev override (ADR 0002).
  2. The Gateway forwards gpt-5.6-sol to the Managed LiteLLM through litellm_proxy/, using an explicit model list rather than a wildcard.
  3. Callers use /v1/responses with an MCP tool and require_approval: "never". The Gateway runs the tool loop itself.
  4. dbt-mcp is pre-installed and pinned, and runs over stdio with max_concurrent_requests: 1.
  5. Only get_lineage_dev, get_node_details_dev and list are enabled. ClickHouse gets a placeholder profile and no credentials (ADR 0001).
  6. The Project checkout is a dedicated read-write copy of the monorepo on the Shared host. It is updated by a manual pull and refresh.sh. The entrypoint runs dbt deps on every start.
  7. Callers share the master key. There is no database, no TLS, and support is best effort from our team.

Checked against source and docs

  • LiteLLM starts a new stdio process for every list_tools and call_tool (MCPClient.run_with_session). Persistent upstream sessions skip stdio. Calls run in parallel unless max_concurrent_requests is set.
  • stdio needs LITELLM_ENABLE_MCP_STDIO=true in the real process environment. Setting it in config.yaml has no effect. The command basename must be on the allowlist (npx, uvx, python, python3, node, docker, deno) or added through LITELLM_MCP_STDIO_EXTRA_COMMANDS.
  • /v1/responses with server_url: "litellm_proxy/…" turns MCP tools into function tools before it dispatches to the provider, and runs them automatically only when require_approval: "never" is set. This was confirmed by reading the code, not by docs.
  • dbt-mcp v2.10.1: DBT_MCP_ENABLE_TOOLS switches off every tool not listed. get_lineage_dev runs dbt parse on every call and reads <project>/target/manifest.json, ignoring DBT_TARGET_PATH (issue #950). get_node_details_dev runs dbt list. Its lock works only within one process.
  • dbt-mcp's console script is dbt-mcp. There is no __main__, so python -m dbt_mcp does not work.
  • dbt-clickhouse main declares dbt-core>=1.9,<2.0 and is tested against 1.12.*.

Assumed, not tested

  • Nothing has been run yet.
  • dbt parse and dbt ls with dbt-clickhouse never open a connection, so the placeholder profile is enough.
  • The time per call is acceptable: process start, the dbt --help probe, then a partial parse.
  • With only three CLI tools enabled, dbt-mcp starts without the dbt platform variables (DBT_HOST, DBT_TOKEN).
  • The responses tool loop works when the model goes through litellm_proxy/, and the Managed LiteLLM passes function tools and streaming through unchanged.
  • The env map on a stdio server reaches dbt-mcp alongside PATH and HOME.
  • The Shared host can reach hub.getdbt.com (or git) for dbt deps at start.

Alternatives considered

  • No Gateway, with IDE agents starting dbt-mcp themselves: rejected, because the Callers are programs.
  • dbt platform Discovery API: rejected. It needs dbt platform jobs and a token, and the metadata would come from outside our host.
  • dbt-mcp as its own HTTP service: rejected. It is documented for debugging only, has no authentication, and would be another service to run.
  • Ask the Managed LiteLLM team to host dbt-mcp: rejected. It depends on their roadmap, and they would need our project on their host.
  • A Devcontainer per developer: rejected in favour of one Shared host.
  • A read-only mount plus a copy at start: rejected. The mounted Project checkout is already a dedicated copy.
  • uvx dbt-mcp: rejected, because it resolves the package on every spawn.

Weak spots to attack

  1. The master key is LiteLLM's admin credential, it is shared with every Caller, and it crosses the network in plain text.
  2. Calls run one at a time and each one starts a process and parses the project. Bursts from several Callers queue up.
  3. The Managed LiteLLM sees one key for everything, and the Gateway has no per-Caller attribution either.
  4. Manual pulls mean the metadata can go stale without anyone noticing.
  5. If dbt deps fails at start (no network, or the hub is down), the Gateway does not come up.
  6. The placeholder profile breaks if profile: in dbt_dwh/dbt_project.yml is renamed.

Open questions

  1. Does the monorepo already have a .devcontainer/ that this one must merge into?
  2. When, if ever, do we add TLS and per-Caller keys? Both need a reverse proxy and a database.
